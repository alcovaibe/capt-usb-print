22.10.2026 владелец слил PR №25 в `main` (`130c158f8288`); CI 123 успешно
прошёл, включая постоянную подпись и обновление APK. Этап D продолжен на этой

Системные PDF используют прежнюю очередь/движок; единственный рабочий исполнитель
общий с прямой печатью. Служба Android не запускает foreground service из фона.

отклоняются. Копии реализует один слой. Чтение pipe ограничено 64 MiB/30 секунд,
с отменой и общим дисковым бюджетом; все страницы готовятся до USB.
Состояния PrintJob и отмена связаны с исходом очереди. После прерывания нет
автоповтора, неопределённый исход не превращается в успешную отмену.
Приватный журнал системной маршрутизации доступен отдельной явной кнопкой.
Автоматические проверки нового PR и аппаратные HONOR-сценарии ещё ожидаются.

### C — аппаратная приёмка 2 отдельных PDF-страниц; следующий контролируемый шаг

Владелец сообщил: после штатного выключения/включения принтера реальная PDF-страница 1 и затем PDF-страница 2 успешно вышли в **двух отдельных заданиях** из подписанной сборки 0.1.0-a2.105. Фото и итоговые JSON двух успешных заданий в эту запись не включены. Это подтверждение именно одностраничного PDF-пути, а не одного общего задания на 2 страницы и не устранения зависания.

Сохраняется воспроизводимый отказ `ReserveUnit` с ответом `A0 A2 08 00 8C 00 00 00`: ранее несколько обычных заданий Stage B также не смогли резервировать устройство, хотя `GetPrinterInfo` работал. Физическое выключение/включение устранило симптом в этот раз, но **устойчивость без перезапуска не подтверждена**. Никакого автоматического сброса или повтора не добавлять.

Новая экспериментальная ветка `feat/stage-c-guarded-pdf-batch`: только PDF, ровно 2–3 итоговых листа, один `ReserveUnit`, книжный A4. Принятый `JobSpecification` определяет порядок диапазона и копий; все отличающиеся страницы последовательно сжимаются **до** USB (не более 4 МиБ/страница, не более трёх листов, повторы могут использовать один неизменяемый растр). Следующий дескриптор идёт только после CAPT-подтверждения предыдущей страницы, между ними `SetJobInfo2(flag=2)`. Отдельное подтверждение, единый процессный PDF-lock и прежний общий USB-lock; неопределённый/частичный исход сохраняется в приватный JSON до ручной отправки. Этап B не изменяется. Физический тест нового режима ещё не выполнен; Stage C не принят.

Дополнительный предохранитель нового пакетного режима: непосредственно перед `ReserveUnit` запрашивается read-only `GetBasicStatus`; при известных NOT_READY/CMD_BUSY/IM_DATA_BUSY/ERROR_BIT (включая наблюдавшийся `0x88`) попытка останавливается **до команды резервирования**. Это не устраняет первопричину зависания, и существующие Stage B/одностраничный PDF-маршруты не изменены.


### C — ревью PR №25: исправления до аппаратного теста

В пакетном движке устранены два дефекта: третий лист больше не вызывает
Stage B-проверку, ограниченную страницами 1–2; `SetJobInfo2(flag=2)` отправляется
ровно один раз после первого листа, как в закреплённом upstream.
Код принятого этапа B не изменён. На модели транспорта проверяется весь
исполнитель с тремя листами, копиями, отказами, отменой и конечным ожиданием.
После каждого подтверждённого листа записывается приватный JSON до следующей
команды; прерванное задание остаётся неопределённым, без автоматического повтора.
Это исправления реализации, **не аппаратная приёмка**. Требуется один тест
PDF 1–3, копий 1, книжный A4, затем ручная отправка JSON. JPEG/PNG-печать,
общая очередь и устойчивость на HONOR пока не приняты.
