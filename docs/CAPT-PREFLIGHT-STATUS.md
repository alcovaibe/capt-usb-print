# Расследование предварительной проверки CAPT в сборке 133

> Историческая контрольная точка, заменённая [LBP2900-STARTUP-CONTRACT.md](LBP2900-STARTUP-CONTRACT.md) после аппаратных отчётов сборки 144. Прежнее требование сохранить запрет по Basic заменено общей политикой LBP2900 Extended/Input. Введённая PR №29 обязательная трактовка ответа SetPowerDown как байта Error была необоснованна и исправлена; обязательные проверки ACK JobInfo/StartPrint/END/Release сохранены.

Задания владельца из HONOR Documents доходили до службы Android и общей очереди документов. Одностраничное и последующее 11-страничное задания полностью подготовились, затем остановились на PREFLIGHT с `A0 E0 06 00 88 00` до ReserveUnit, отправив ноль байт печатных данных. Разрешение USB и захват без принуждения были доступны. Владелец помнит выключение/включение питания; отчёты не доказывают момент этого действия и не содержат свежего парного снимка расширенного состояния этих попыток.

Нельзя смешивать эти отказы с историческими ответами ReserveUnit `0x8C`. В старой диагностике есть Basic `0x88`, Extended Bas=`0x01` / Bas1=`0x88` и последующее успешное задание этапа B. Это не атомарный снимок и не доказательство правильности обхода Basic `0x88`. Описываемый исторический PR сохранял эту остановку.

## Аудит исходников и ограниченное изменение

- [Закреплённый ValdikSS capt-status.c](https://github.com/ValdikSS/captdriver/blob/892f320c019974a5b737e000fcc2c8582264a131/src/capt-status.c) читает базовое состояние, условно обновляет расширенное и читает входное при NEED_INPUT_STATUS.
- [Закреплённая подготовка LBP2900/3000](https://github.com/ValdikSS/captdriver/blob/892f320c019974a5b737e000fcc2c8582264a131/src/prn_lbp2900.c) обрабатывает изменения InputStatus до резервирования. Автоматическая разрушающая очистка/повтор исходного проекта здесь не заимствована.
- [Закреплённые флаги](https://github.com/ValdikSS/captdriver/blob/892f320c019974a5b737e000fcc2c8582264a131/src/capt-status.h) называют базовые биты 0x08/0x80 IM_DATA_BUSY/ERROR. Более старые [флаги agalakhov](https://github.com/agalakhov/captdriver/blob/175f8ff4464591feb67728c7752ac752c7b48d43/src/capt-status.h) используют другие названия; ни один источник не доказывает допустимость постоянного короткого ответа этого принтера.

В этой версии обработчик документов снимал парные Basic/Extended, обрабатывал запрошенный InputStatus и перечитывал оба ответа до резервирования. Переходная занятость, ожидающий ввод, выдача бумаги и незавершённые страницы опрашивались ограниченно: до 21 выборки в пределах бюджета опроса 5 секунд с паузами 250 мс. Ограниченная задержка транспорта добавляется отдельно; это не общий пятисекундный срок для USB. Отмена проверялась перед каждым запросом и между выборками. Аппаратные/ошибочные/бумажные флаги ExtendedStatus и некорректные ответы останавливали работу немедленно. Начальное состояние только с ожиданием/офлайном допускало прежнюю подготовку задания после снятия запрета Basic.

Постоянный запрещающий Basic при в остальном свободном Extended давал `CAPT_STATUS_CONFLICT`, а не объявление аппаратной неисправности или успешной печати. Постоянная согласованная занятость/ожидание оставались `PRINTER_STATUS`; неполные/некорректные кадры — `CAPT_STATUS_INVALID`. Необработанные кадры (до 64 байт на запрос) сохранялись в ограниченной трассе JSON задания; это служебные данные, а не содержимое документа. Поле последнего кадра теперь закономерно содержало самый свежий Extended/Input, поэтому парный Basic следовало искать в трассе.

Новые команды изменения состояния, повтор резервирования, сброс, сервисные команды и автоматический повтор задания не добавлялись. Подпись, разрешения, растр и последовательность этапа B не менялись. Квоты исходников/очереди и ручной экспорт сохранялись. Повторяющийся Basic `0x88` всё ещё мог блокировать все документы; без новых аппаратных данных исправление первопричины не заявлялось.

## Проверки и следующая аппаратная попытка

Чистые тесты состояния и полного обработчика покрывают зафиксированный постоянный конфликт, временное снятие запрета, флаги ввода в любом ответе, неснимающийся запрос ввода, бумажные/аппаратные ошибки, незавершённые страницы/выдачу, некорректные/отсутствующие счётчики, отмену, пределы времени/выборок и выполнение с одним резервированием без повтора. Синтетические изменения моделируют ошибки и не выдаются за физические трассы. CI PR должен собрать приложение, выполнить lint, все JVM-тесты и существующие проверки растра/системной печати API 36.

После успешного CI, просмотра и отдельно запрошенной подписанной сборки:

1. Обновить подписанный APK поверх установленного и выдать доступ подключённому LBP2900.
2. Один раз отправить **новое задание A4 на одну страницу и одну копию** из HONOR Documents. Не менять питание во время попытки, чтобы парные выборки описывали один запуск.
3. Отправить JSON нового задания и системной печати, сообщить о выходе листа. При постоянном конфликте должны быть повторные парные ответы, ноль печатных байтов и отсутствие резервирования. После одной неудачной/неопределённой попытки остановиться.

Пока предварительная проверка не разобрана, не просить повторных 11-страничных попыток. Физическая приёмка этапа D, точные поля, поведение второго приложения-источника и восстановление ReserveUnit оставались открытыми.

## Продолжение расследования — 23 октября 2026 года

Короткий Basic имеет корректный транспортный формат, но семантика его состояния в конкретной фазе не проверена. Он больше не представляется доказанной аппаратной ошибкой. На этой исторической точке ограниченная предварительная проверка сохранялась до получения аппаратных данных. Проверки ACK, повторные выборки UNKNOWN/Input, ограниченная трасса обмена сеанса и остававшееся аппаратное решение описаны в [CAPT-PROTOCOL-FOLLOWUP.md](CAPT-PROTOCOL-FOLLOWUP.md). Это не обход 0x88 и не продемонстрированное исправление печати.
